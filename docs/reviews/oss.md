# oss review

- **Role**: oss v1
- **Date**: 2026-09-15
- **Scope**: the whole pi-coding-agent-extensions monorepo: the 8 published packages under packages/ plus the repository root (governance, license, release, community, funding surface)

## Lens coverage

Each lens required by this run, applied to the scope, and the findings that answer it. All seven
apply to this scope; none is not applicable.

| Lens | Findings | Verdict |
| ---- | -------- | ------- |
| Governance a new contributor can find and follow | OSS-02, OSS-03, OSS-05 | Fails. No CONTRIBUTING.md, no code of conduct, no GOVERNANCE.md. The only governance artifact that exists is `docs/adr/`, which holds 12 accepted ADRs after this session, and nothing links to it. |
| Contribution path from first issue to merge, and where it stalls | OSS-02, OSS-05, OSS-09 | Fails at the first step. There is no issue template and no path document, and the merge gate is a no-op because `pnpm lint` echoes and `pnpm format` cannot match a file. |
| CLA or DCO the project asks for, and whether it is enforced | OSS-02, OSS-15 | Neither exists, and it is enforced nowhere. `web_commit_signoff_required` is false. Recorded as a deliberate inbound=outbound `MIT` choice, not as an oversight, and made consistent by OSS-15. |
| Funding transparent to donors and independent of one payer | OSS-06 | Fails. There is no funding surface at all, so the project is 100% single-payer with no defined donor relationship. |
| Release cadence contributors can plan around | OSS-07, OSS-12, OSS-16, OSS-17 | Partially passes. OSS-07 landed, so the tree is releasable again, but no cadence is documented, there are 0 GitHub Releases, there is no root changelog, and the dry-run summary misreports. |
| Community whose decisions are documented, not remembered | OSS-05, OSS-12, OSS-14 | Partially passes. `docs/adr/` is genuinely strong for architectural decisions and `docs/handoff/` records session state, but there is no governance record, no public roadmap, and no community venue. |
| Boundaries between maintainers and donors, and who decides on conflict | OSS-05, OSS-06 | Fails. No donors exist and no boundary is written, so the question is currently undefined rather than answered. |

## Decisions taken on this run

Put to the maintainer and answered before the plan was written, so each is a recorded decision
rather than an assumption. They are what turns the CI, contribution-terms, governance and funding
lenses into a shape the plan can execute.

| Question | Decision | Consumed by |
| -------- | -------- | ----------- |
| Should CI be reintroduced, given the earlier deliberate removal of `.github/`? | No. Keep zero CI on purpose and document the gaps as accepted risks. | OSS-17, and the "Deliberately not in this plan" section of the plan |
| Is the uncommitted dependency bump in the working tree intentional? | Yes, intentional and uncommitted. The plan must include committing it properly. | OSS-07 |
| Which inbound license term applies? | Neither CLA nor DCO: inbound=outbound under `MIT`, documented as a deliberate choice. | OSS-02 sub-step 2.2, OSS-15 |
| Which governance model should be documented? | BDFL / single maintainer, written down explicitly. | OSS-05 |
| What should the project do about funding? | Set up a transparent funding surface: GitHub Sponsors, `FUNDING.yml`, documented use of funds, and a maintainer/donor boundary. | OSS-06 |
| Is the 72-hour dependency cooldown still wanted? | No. Remove it: the repository consumes the newest dependency versions and accepts the supply-chain tradeoff recorded in ADR 012. | OSS-20, ADR 012 |
| How should the stale per-package lockfiles be handled? | Refresh all eight and ship them in the same commit as the manifests they match. | OSS-19 |
| Which linter, given that typescript-eslint cannot run on TypeScript 7? | Biome 2.5.13: it parses TypeScript 7, ships as one binary, and pulls no peer dependencies, unlike the ESLint setup the previous session used. | OSS-09, OSS-21 |
| Who owns formatting, prettier or the committed style? | Prettier. The 162 files that disagreed with .prettierrc were reformatted in one mechanical commit. | OSS-09 |
| What response time should the security policy promise? | Acknowledge a vulnerability report within 3 working days, then confirm or dismiss it. | OSS-04 |
| Is the absence of `package-lock.json` and of a `packageManager` field intentional? | Yes. pnpm only, with the pnpm lockfile per package; every `package.json` is meant to look that way. | OSS-07, OSS-08 |
| Are `packages: []` at the root and the per-package `overrides`/`allowBuilds` divergence intentional? | Yes. Each package is a standalone pnpm project carrying only the dependencies it needs, and the root is a script runner rather than a workspace. | OSS-08, OSS-10 |

## Accepted risks

These are findings whose remediation the maintainer declined by decision, so what the plan
carries is a record, not a fix. They are listed here so no reader mistakes silence for resolution.

- **OSS-17, resolved as a record.** No CI, 0 of 8 packages provenance-attested, releases
  published from a developer machine with a personal npm credential, tags lightweight and
  unsigned. ADR 013 states the decision and the exposure, and SECURITY.md publishes it. The
  exposure itself is unchanged and stays accepted.
- **OSS-18, still open.** No dependency-update automation, and dependabot pull request #2 open
  since 2026-09-11, on a repository whose only open item it is.
